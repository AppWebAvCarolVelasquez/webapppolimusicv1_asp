### Permission Learning
- IIS_IUSRS = app pool worker identity (file access when not impersonating)

- Both must be granted for Classic ASP sites to work with Windows Auth DB access

## Session 7 — REAL ROOT CAUSE of 800a0409 FOUND and FIXED (Option Explicit was only layer 1)

### Symptom after Session 6 fix
- ztest2.asp (functions.asp only) → 200; default.asp → 302; BUT login.asp still → 500 "Error de compilación en Microsoft VBScript error '800a0409'" (Out of string space / unterminated string)

### Diagnosis path (no IIS round-trip needed)
- Byte-level checks ruled out long lines (max 224 chars), BOM, encoding; wwwroot files confirmed byte-identical to Desktop; include graph has no cycles
- Isolated the delta: pages including database.asp fail; pages including only functions.asp work; database.asp UNIQUELY contains literal `<%` / `%>` sequences inside VBScript strings (the six Replace() calls in the ExecuteGlobal secrets.asp loader)
- Root cause: the IIS ASP tokenizer is DELIMITER-BASED, NOT string-aware. `"<%"` inside a string terminates/restarts the script block, splitting `Replace(secretsContent, "` mid-string → unterminated string constant → 800a0409 on EVERY page that includes database.asp. (Explains why the professor's app always worked and ours never did.)
- cscript.exe is blocked (LOLBin) in this environment, so offline compile simulation was replaced by static analysis

### Fix applied — config/database.asp
- Rewrote delimiter stripping using concatenation: `Replace(x, "<" & "%", "")`, `Replace(x, "%" & ">", "")`, `"<" & "%" & vbCrLf`, `vbCrLf & "%" & ">"`. Runtime behavior for stripping secrets.asp delimiters is identical.

### New tool — tools/asp_parse_check.py
- Emulates IIS tokenizer + runs a VBScript string/comment-aware quote-balance check on every code chunk
- Negative control (old buggy pattern) FAILS at the exact offending line; all 9 pages (default, login, songs, logout, denied, admin ×4) pass OK after the fix
- Deleted obsolete diagnostic merge_check.py + merged_login.vbs

## Session 11 — Bug de SESION: RegenerateSession destruia la sesion tras login

### Sintoma (test_e2e.bat v1)
- POST login correcto: 302 -> songs.asp (las credenciales VALIDAN bien)
- PERO: songs.asp con la misma cookie -> 302 otra vez a login. La sesion NO persistia.
- Resultado: usuario "autenticado" pero siempre deslogueado.

### ROOT CAUSE: contrato roto en RegenerateSession() (includes/functions.asp)
- Hacia: Session.Abandon + Session.Contents.RemoveAll() + reescribir Session("ID_USER")... + **Response.AddHeader "Set-Cookie", "ASPSESSIONID=; ...Expires=1970"**
- El Set-Cookie BORRABA la cookie que el cliente necesita, mientras el codigo "restauraba" datos en una sesion ya marcada para destruir. Contradiccion total -> sesion perdida en la siguiente peticion.
- Antipatron conocido: la regeneracion de SessionID en Classic ASP NO es fiable; Session.Abandon invalida la sesion y cualquier escritura posterior no persiste.

### FIX
- Reemplazada `RegenerateSession()` por `ResetSessionForLogin()` en includes/functions.asp: hace `Session.Contents.RemoveAll()` + emite un `Session("CSRF_TOKEN")` nuevo (invalida tokens conocidos) + NO abandona la sesion ni toca Set-Cookie.
- login.asp actualizado: `Call ResetSessionForLogin()` y luego asigna Session("ID_USER"/"USERNAME"/"USER_TYPE"/"CSRF_TOKEN").
- Se mantiene la mitigacion de session fixation de forma que SI funciona en Classic ASP (limpiar estado pre-login + rotar CSRF + cookie ASPSESSIONID de IIS + timeout corto).
- logout.asp: el Session.Abandon + borrado de cookie AHI es correcto; mejorado para leer el nombre real de la cookie desde HTTP_COOKIE (soporta cualquier ASPSESSIONID*) en vez de nombres hardcodeados.
- asp_parse_check: 9/9 OK.
